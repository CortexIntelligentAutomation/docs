### Features

#### Capability

##### Added AI-generated flow documentation

{{% ctx %}} can generate a human-readable document for each flow in a package. Generation runs on the customer's network. The documentation service calls a local model server and does not call a cloud service at runtime.

Callers submit a self-contained package to `POST /documentation` and receive a job id. `GET /documentation/{jobId}` returns the job status and, when a flow has been documented, the key of its document. The document key is the flow id. A job can be polled while it runs. Completed, pending, and failed flows are counted separately, and those counts add up to the number of flows in the package.

When every flow is documented, the job status is `Completed`. If some flows are documented and others fail, the job status is `CompletedWithErrors` and the successful documents can still be retrieved. A flow that is generated with gaps stays in the completed set and is marked partial. A flow that cannot be documented is reported with a reason of `NotFound`, `TooLarge`, or `Failed`, and no document is produced for it. If the model server cannot be reached, the job status is `Failed`. Submitting that same package again, after the model server is available, continues the pending flows and leaves documents that were already produced unchanged. Submitting a package that has already completed returns the same job id and does not generate the documents again.

A job can be cancelled. A cancelled job is not resumed. The same operation can purge the job.

Each document contains:

* Flow name, type, compatibility version, description, and non-default flow settings, with a short overview of what the flow does
* Input, output, and internal variables, including default values, and the flow and block exception handlers
* Flows called by the flow, including the calling block, workspace, inputs passed, and output received
* A walkthrough of each workspace in execution order, including decision branches, loops, and error paths, plus a variable usage matrix
* A count of the block types used
* A review with a score, pros, cons, and suggestions

Unset values are shown as `(not set)`. Encrypted default values are shown as `[encrypted]`. Names, structure, variables, and counts are taken from the flow. Overview text, purposes, and the review are written by the model. A flow that is too large for one model pass is split and stitched into one document. If the model leaves a section empty, that section is retried a bounded number of times and any remainder is left visible as not generated. Very long configuration values are truncated. A called sub-flow is named when the reference can be resolved. A dynamic reference is labelled as dynamic. The processor does not load other flows to resolve it.

The review always includes a warning that it is a machine-generated draft and must be checked by a person before it is relied on. Structural findings are added to the cons from the flow itself: unused or mis-scoped variables, duplicate block labels, unreachable workspaces, and unmatched wireless senders. Blocks that are present but not connected are noted in the workspace walkthrough.

Generation can be limited to run windows. When scheduling is disabled, a job starts immediately. When scheduling is enabled, a job submitted outside a window is accepted with status `Paused` and starts when the next window opens. At the end of a window, the model call in progress is cancelled, documents already completed are kept, and the job returns to `Paused` until the next window. The interrupted flow is generated again from the start. Windows use the node-local time. `Start` and `End` use `HH:mm`. A window whose end is earlier than its start runs through midnight. Days can be named `Mon` or `Monday`, and the same forms for the other days. If `Days` is omitted, the window applies every day. Overlapping windows on the same day run from the earliest start to the latest end. A duplicate day in one window is ignored. A window that cannot be read, uses an unknown day, or has the same start and end, stops the service at startup with a configuration error.

```json
{
  "Scheduling": {
    "Enabled": true,
    "Windows": [
      { "Days": ["Mon", "Tue", "Wed", "Thu", "Fri"], "Start": "20:00", "End": "06:00" },
      { "Days": ["Sat", "Sun"], "Start": "00:00", "End": "23:59" },
      { "Days": ["Mon"], "Start": "12:00", "End": "13:00" },
      { "Start": "05:00", "End": "05:30" }
    ]
  }
}
```

##### Added running execution counts and details

The [{{% ctx %}} API Gateway Service][] now exposes running-execution information that the [{{% ctx %}} Gateway][Gateway] uses for live counts and lists.

* `api/{tenant}/{system}/executions/count` returns the total number of running executions.
* `api/{tenant}/{system}/executions/counts` returns running-execution counts by package name and package version.
* `api/v2/{tenant}/{system}/executions` returns the running executions.

Each route accepts `packageName` and `packageVersion`. Omitting both returns data for every package and version. Supplying only `packageName` returns data for that package across its versions. Supplying both returns data for that package version. Supplying `packageVersion` without `packageName` is rejected.

In [{{% ctx %}} Gateway][Gateway]:

* The Operations Overview running-executions tile shows the total, and refreshes while the page is open.
* The Packages page shows a running-executions count on each package version. A collapsed package row shows the count for the current version and how many more are running on older versions.
* The Running Executions tab for a package version lists that version's executions, including execution id, parent, root, started at, duration, executing on, and debugged by.

Each view stops calling the API when it is closed and nobody else is viewing it. Two people viewing different package versions each receive only the executions for the version they have open.

##### Added proxy support to Send Email Using Microsoft 365

The Send Email Using Microsoft 365 block has an optional advanced `Proxy` property, listed below the credentials. When it is set, Microsoft 365 authentication and Graph API traffic use that HTTP or HTTPS forward proxy. `Proxy` defaults to empty. On a literal proxy, `Host` defaults to empty, `Port` defaults to `8080`, `Type` defaults to `HTTPS`, and proxy credentials default to empty.

Existing flows are upgraded so the property is present. When `Proxy` is left unset, the block still sends mail with the configured credentials.

##### Added SSH private key authentication

The Execute SSH Command block can authenticate with a private key file. `SshCertificateCredentials` accepts a PuTTY PPK file (`SshCertificateStoreType.PpkFile`), including a password-protected PPK when the certificate password is supplied. A missing PPK file fails with `SSHClientException` error code 303. An incorrect password for an encrypted PPK fails with error code 280. Any other certificate store type fails with an `SSHClientException` whose inner exception states that the certificate store type is not supported.

##### Introduced the {{% ctx %}} Portal

The {{% ctx %}} Portal is a new web application. After sign-in, a sidebar shows the {{% ctx %}} icon and the portal version. Apps opens a flat list of approved micro-applications. Typing in the list filters it by name, and clearing the filter shows the full list again. Choosing an application opens it in the shell. Back to Home closes the application and leaves the sidebar in place.

A micro-application is described by a manifest. The manifest requires identity, remote entry, compatibility, and security fields. Permissions and allowed backend hosts are optional. An application whose manifest fails validation, including a compatibility mismatch, is not offered as a loadable application. When an approved application cannot load, the shell shows a message that it cannot be opened.

Professional Services can start a new micro-application from the supplied template and build it with the portal UI kit, including list, table, accordion, divider, label, and blockquote controls.

#### Security

##### Added certificate-based OAuth and mTLS

Machine-to-machine applications can now be registered with one authentication method.

* A secret uses the OAuth 2.0 client-credentials grant. The application receives a bearer token from `POST /oauth/token` and calls protected APIs with that token.
* A leaf certificate uses mutual TLS at the API. The application does not use a bearer token.

Registration supplies either a client secret or one or more leaf certificates. An application cannot be registered with both, or with neither. The method stays in place for the life of the application.

##### Added TCP passthrough for API Gateway mTLS

The generated load-balancer configuration for the [{{% ctx %}} API Gateway Service][] TLS listener now uses TCP passthrough. The load balancer does not terminate and re-encrypt that path, and it does not present its own client certificate there. A registered OpenIddict mTLS client can authenticate through the load balancer, including `oauth/token`, without a manual edit of the go-between configuration. Password-grant calls continue to work through the load balancer.

##### Required HTTPS for a remote AI model server

When the documentation service uses a model server on the same machine at `127.0.0.1`, it can use HTTP and does not require an API key. When the model server is on another machine, the endpoint must be HTTPS and the API key must be stored as encrypted text. Requests to that server send the decrypted key as a bearer token. The service does not start when a remote endpoint uses HTTP, when the API key is missing, or when the API key is plain text.

Affected Components:

* {{% ctx %}} Documentation service

##### Keeping portal sign-in tokens out of the browser

Portal sign-in establishes a session with an encrypted cookie. The gateway auth token is stored in that cookie and is not written to browser storage. A failed sign-in does not issue a session cookie and the password is not written to the audit record. A page that requires a session sends a signed-out user to the sign-in page. The portal does not use a bearer token in the browser.

A signed-in user sees their display name or username in the header, and can sign out from the header. A platform administrator also sees `Platform Administrator` on that same line. The current-user response includes role names and does not include a security token.

##### Added an optional OpenID scope and UserInfo

When the scope includes `openid`, the grant also issues an ID token, and a later refresh keeps `openid` and issues a new ID token. A scope that is not recognised is rejected with `invalid_scope`.

`GET /oauth/userinfo` is available to tokens that include `openid`.

##### Updated the SSL best practices scripts

The SSL best practices scripts now apply the following hardening on supported operating systems:

* Triple DES 168 is disabled.
* The SHA hash is removed.
* `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384` and `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` are enabled so communication with Microsoft services, including NuGet, continues to work after hardening.

On Windows Server 2022 and later, the scripts set these cipher suites:

* `TLS_CHACHA20_POLY1305_SHA256`
* `TLS_AES_256_GCM_SHA384`
* `TLS_AES_128_GCM_SHA256`
* `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`
* `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`
* `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`
* `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`

On supported operating systems older than Windows Server 2022, the scripts set these cipher suites:

* `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`
* `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`

#### Installation

##### Added AI model server installation scripts

Installation scripts are provided for the AI model server used by flow documentation. The entry-point script follows the {{% ctx %}} installation conventions. It stops if the EULA is not accepted, and `-WhatIf` lists the steps without changing the machine. A failed prerequisite check stops the installation. If the Visual C++ runtime is missing or out of date, the script installs the runtime shipped with the artefact.

The script installs the model server and the model, runs the server as a Windows service, and reports success only after the model has loaded. If a new build fails to start, the existing installation keeps running. On the web application server, only that server can connect to the model server. On a separate server, the model server accepts only HTTPS with the API key, the certificate and API key are readable only by the service account and administrators, and the firewall allows the web application server. Running the script again keeps the existing API key unless a new key is requested. A generated key is shown once and is not written to the log. A failed step stops the installation and is written to the log.

##### Schedules that cannot fire are rejected

A bug was fixed where a schedule whose CRON expression has no fire time after the current time could be saved, and where creating that schedule through the API could time out. Saving it could also break the [{{% ctx %}} Scheduling Service][] on a role change.

In the [{{% ctx %}} Gateway][Gateway], the CRON field shows `The CRON expression is invalid as its execution times are in the past.` and Save stays disabled. The expression is checked after the field has been idle for 250ms, and the schedule is not stored.

Through the API, the same CRON is rejected with HTTP 400 and problem type `InvalidCronSchedule`. The detail is `Schedule specified for the flow has invalid cron. Reason: The CRON expression is invalid as its execution times are in the past.` The schedule is not stored.

A CRON that still has a future fire time, including a one-shot that has not yet occurred, is stored and added to the scheduler. The API returns HTTP 200.

### Known Limitations

* AI-generated flow documentation does not remove secrets from the generated document. Encrypted default values are shown as `[encrypted]`. Other secret values in the flow are written as they are stored.
* The documentation service does not enforce cross-tenant access control.
* The review section of a generated flow document is a machine-generated draft. It has a measured false-positive rate, it can miss issues, and it must be reviewed by a person before it is relied on.
* A flow that is too large for the model, even after it is split, is reported as `TooLarge` and is not given a document.
* Documentation run windows use the clock on the node. The feature does not apply a separate daylight-saving adjustment.
* Send Email Using Microsoft 365 can use an HTTP or HTTPS forward proxy. SOCKS proxies are not supported.
* SSH private-key authentication supports PuTTY PPK files only.
* NuGet updates in this release do not include log4net. The log4net package is unchanged.
* Windows Server 2025 was tested for {{% ctx %}} without {{% ctx %}} 7 components.
* The {{% ctx %}} Portal site is served from a single origin. Split-origin hosting is not supported.
* Portal micro-applications use the portal UI kit. Native HTML form controls are not supported in a micro-application.
